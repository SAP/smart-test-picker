# Round 4: generic executor attribution boundary

## Conclusion

**Chosen direction: EXTENDED CALL-SITE REWRITING.**

**Final decision: GENERIC EXECUTOR ATTRIBUTION PARTIALLY SUPPORTED.**

The safe increment is to recognize `execute`/`submit` call-site owners whose class-file hierarchy reaches
`Executor` or `ExecutorService`. The transformer reads hierarchy metadata through the transforming class's
loader and never loads or initializes a referenced class. This covers the requested ordinary calls made by
eligible non-bootstrap bytecode, including concrete `ThreadPoolExecutor` owners, custom executor interfaces,
and custom implementations. It remains structurally incomplete because calls made in excluded bootstrap/JDK
bytecode are not rewritten. The explicit-executor `CompletableFuture` probe demonstrates that limit.

This POC should remain an experimental, opt-in part of the ASM collector only if any emitted
`executor-attribution-incomplete` or `executor-attribution-unsupported` diagnostic makes the resulting map
ineligible for precise RTS. It is not a sound universal executor attribution mechanism.

## Strategy A: extend call-site rewriting

The JVM invocation records a symbolic owner, method name, and descriptor. Exact-owner matching from Round 3
was unnecessarily narrow: the owner class file can be walked through its superclass and interface names until
`java/util/concurrent/Executor` or `ExecutorService` is reached.

The implementation uses `ClassLoader.getResourceAsStream(owner + ".class")` and ASM header metadata. It does
not use `Class.forName`, verifier-driven common-superclass computation, reflective linkage, or class
initialization. Consequently it does not introduce transformation-time initialization cycles. The currently
transforming class's already-supplied `ClassNode` is used when it is itself the invocation owner.

The limitations are important:

* A loader need not expose bytes for every class it can define. Generated, hidden, encrypted, mutable, or
  unusual loader-owned types can therefore be unresolved.
* The resource returned by a nonstandard loader can differ from the definition that will actually link.
* An absent parent anywhere on a potentially relevant hierarchy makes the result `UNKNOWN`, not `NO`.
* An unresolved executor-shaped invocation is left unchanged and emits an
  `executor-attribution-incomplete:<caller>:<owner>.<method><descriptor>` diagnostic. This avoids both unsafe
  guessing and a silent false-negative map. It can conservatively flag a non-executor with an unavailable
  hierarchy; that false alarm is preferable to false precision.
* Calls from bootstrap classes are deliberately excluded. Calls in eligible framework classes can be covered
  if loaded after `premain` and their hierarchy bytes are available, but this is not a framework guarantee.
* Reflection, method handles, dynamically generated bytecode loaded outside the transformer, and APIs which
  accept tasks and later submit them from JDK code remain invisible.

The resolver is intentionally uncached in this POC. This avoids pinning application class loaders and avoids
stale answers for mutable loaders, at the cost of repeated class-resource reads during transformation. A
production implementation could use weak, loader-scoped caches, but that is not required to prove the claim.

False positives are bounded by requiring both a supported method descriptor and a proven executor hierarchy.
False negatives remain possible only at the explicit unresolved/excluded/dynamic boundaries above. Supporting
more task-taking APIs would require individual semantic rules rather than a broad method-name heuristic.

## Strategy B: executor implementation boundary

`ThreadPoolExecutor.execute` is attractive because it is the real acceptance boundary and naturally sees
submissions originating in `CompletableFuture`. It is not a safe narrow collector change:

* `ThreadPoolExecutor`, `AbstractExecutorService`, their queue/run machinery, and common JDK executors are
  bootstrap classes. Transformed code cannot resolve application-class-loader `RuntimeHooks` without appending
  helper code to the bootstrap search path or introducing another bootstrap-visible bridge.
* These classes are normally loaded before application agents finish initialization. Reliable attachment would
  require retransformation support, retransformation-capable manifest flags, and careful startup ordering.
* Java modules, bootstrap package visibility, CDS/runtime-image behavior, and JDK implementation changes become
  compatibility inputs. Instrumenting `runWorker`, queues, or private internals is still more version-sensitive.
* Agent ordering with other bytecode agents becomes observable. Every transformer must accept the bytes left by
  preceding agents, and retransformation behavior is not uniformly compositional.
* Instrumenting only JDK executors still misses custom/framework executors. Instrumenting every implementation's
  `execute` method requires hierarchy resolution anyway and risks double wrapping at delegating boundaries.
* Wrapping at acceptance changes the object observed by rejection handlers, queues, `beforeExecute`, and
  `afterExecute`. Instrumenting a run boundary instead needs a side association with lifecycle, cancellation,
  reuse, and retention problems.

`AbstractExecutorService.submit` is not a universal boundary: implementations may override it, and custom
`Executor` types need not extend that class. Queue instrumentation is lower-level than the requested contract
and cannot reconstruct submitter context unless context was attached earlier. Strategy B therefore adds
bootstrap coupling and semantics risk without actually making the boundary universal.

## Implementation changes

`ExecutorCallSiteTransformer` now:

1. recognizes the four Round-3 descriptors (`execute(Runnable)`, both `submit(Runnable...)` forms, and
   `submit(Callable)`);
2. proves that the symbolic owner is an executor by recursively reading superclass/interface class files;
3. wraps only on `YES`, leaves `NO` alone, and diagnoses `UNKNOWN`;
4. recognizes explicit-executor `CompletableFuture.runAsync`/`supplyAsync` call sites as unsupported and emits
   an `executor-attribution-unsupported` diagnostic; and
5. continues excluding bootstrap/JDK, STP, and ASM implementation classes, preventing recursive STP
   instrumentation.

No runtime propagation semantics changed. `RuntimeContextService` still snapshots the active `TestIdentity` at
submission, installs it for the wrapper invocation, clears/restores the finished marker, and restores the exact
prior worker state in `finally`.

## Exact support boundary

Supported when an eligible, transformed non-bootstrap class contains an `invokeinterface`, `invokevirtual`, or
other method invocation whose symbolic owner can be proven to implement/extend `Executor` or `ExecutorService`:

* `execute(Runnable)`;
* `submit(Runnable)`;
* `submit(Runnable, Object)`; and
* `submit(Callable)`.

This includes interface-typed `ExecutorService`, direct `ThreadPoolExecutor`, inherited methods whose symbolic
owner is the concrete subtype, custom interfaces extending the executor interfaces, and custom implementation
types. A custom implementation that delegates through a supported call site is also covered; already-wrapped
tasks can be wrapped again, which preserves attribution but adds identity/allocation changes.

Unsupported:

* a supported-looking owner whose hierarchy bytes cannot be resolved (diagnosed);
* submission calls originating in excluded JDK/bootstrap code;
* `CompletableFuture` async APIs, including their explicit-executor overloads, when the runtime executor itself
  is a JDK implementation (recognized application call sites are diagnosed);
* `invokeAll`, `invokeAny`, scheduled/periodic APIs, ForkJoin, virtual threads, structured concurrency,
  reflection, method handles, reactive work, HTTP/server correlation, and remote JVMs;
* generated/hidden callers not observed by this transformer; and
* application or framework code already loaded before transformer registration (the POC does no
  retransformation).

## CompletableFuture diagnostic

`CompletableFuture.runAsync(applicationTask, directThreadPool)` does **not** get captured. Application bytecode
calls `CompletableFuture.runAsync`, not `Executor.execute`, so it does not match the wrapping rule. JDK
`CompletableFuture` code later invokes the supplied executor's `execute`; that call site is in excluded bootstrap
bytecode. The application method is consequently recorded as `NO_ACTIVE_TEST`, and the caller produces an
`executor-attribution-unsupported` diagnostic.

The same reasoning applies to `supplyAsync`. A custom executor whose own application bytecode delegates through
a supported call site may incidentally restore coverage, but that is a property of that implementation and is
not claimed as `CompletableFuture` support. Covering a JDK executor reliably would require instrumenting
`CompletableFuture` or a JDK executor boundary, or changing the application to pass a context-aware executor;
the transparent alternatives are JDK/bootstrap instrumentation and are out of scope.

## Safety and observable semantics

There is no global thread binding. Each wrapper captures one immutable logical submission context and scopes it
to `run`/`call`; `finally` restores both the exact previous active context and previous finished marker. Pool
reuse, nesting, failure, late execution, and no-context operation therefore do not leak A into B. With no active
test (or no runtime), `RuntimeHooks.wrap` returns the original object. Rejection never invokes a wrapper, and a
cancelled `FutureTask` never invokes its nested source wrapper.

The wrapper returns the exact Callable result and rethrows the exact throwable. It does not catch, translate, or
swallow failures. For `submit`, the executor still creates its normal `FutureTask`; only the source task nested
inside it changes. Cancellation and result behavior are retained.

Wrapping is nevertheless observably different for identity-sensitive executors:

* direct `execute` queues the wrapper, so queue inspection sees a different `Runnable`;
* `remove(originalRunnable)` can fail because the queue contains the wrapper;
* `beforeExecute`/`afterExecute` observe the wrapper for direct `execute` (and normally the executor-created
  `FutureTask` for `submit`);
* custom executors that compare, classify, cast, annotate, or map commands by object identity can behave
  differently; and
* delegating executor call sites can create multiple wrappers.

These are inherent wrapper semantics, not repaired by hierarchy recognition. Broadly enabling this mechanism
for unknown identity-sensitive executors would be unsafe; that is a principal reason for the partial verdict.

## Unsupported-attribution policy and recommendation

The output already has an `agentErrors` array. This round places bounded, machine-readable incompleteness facts
there rather than inventing selection behavior:

* `executor-attribution-incomplete` means an executor-shaped owner could not be classified safely;
* `executor-attribution-unsupported` means a known escaping API shape was observed.

Any such fact should force conservative RTS fallback for the affected collection/run. Absence of a diagnostic
does not prove absence of invisible reflection, preloaded/generated code, or JDK-internal submission, so teams
with executor-heavy tests or unsupported async APIs should also select conservatively by configuration. The
collector should retain this only as explicitly partial evidence, with the four supported descriptors declared
as its contract. It should not advertise generic async coverage or silently use the map as complete.
